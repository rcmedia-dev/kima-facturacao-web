2Modelo multitenant (isolamento empresa/pessoa)

2.1 Como o isolamento funciona hoje (padrão kima_rh)

  • Usuário = auth.users → perfil humano em public.profiles (id = auth.uid())
  • Organização ou Pessoa = public.companies (campo org_type: 'company' | 'person')
  • Vínculo = public.memberships (user_id → company_id, com role e status)
  • Licença = public.company_modules (company_id → module_key, status='Ativo')

2.2 Funções de segurança compartilhadas (reutilizadas)

Já existem no public (security definer) e serão usadas nas políticas RLS do módulo:

public.is_company_member(company_id uuid)   → boolean
public.is_company_admin(company_id uuid)     → boolean
public.has_active_module(company_id, 'faturas') → boolean

Módulo faturas confirmado no catálogo public.modules (Kima Faturas).

2.3 Regra de isolamento (a aplicar em TODAS as tabelas)

-- Cada tabela do módulo terá:
company_id  uuid NOT NULL REFERENCES public.companies(id) ON DELETE CASCADE
created_by  uuid REFERENCES auth.users(id)   -- quem criou
updated_by  uuid REFERENCES auth.users(id)   -- última alteração

-- RLS habilitado com 4 políticas por tabela:
SELECT  → USING (is_company_member(company_id))
INSERT  → WITH CHECK (is_company_member(company_id) AND has_active_module(company_id, 'faturas'))
UPDATE  → USING (is_company_member(company_id))
           WITH CHECK (is_company_member(company_id) AND has_active_module(company_id, 'faturas'))
DELETE  → USING (is_company_admin(company_id))

Efeito prático: cada empresa/pessoa só enxerga e altera os seus próprios registos. Admin pode apagar; membro com licença ativa cria/edita; qualquer membro vê. Ninguém acede a dados de outra organização.

4.2 Reescrita de db/queries.ts (PostgREST)

Hoje usa drizzle.query(...) sobre o cliente supabase-js, o que não funciona. Será reescrito com a API nativa do supabase-js (.from('clientes')) mantendo os mesmos nomes de função. A RLS garante o isolamento automaticamente — nenhum WHERE company_id manual vaza dados.
